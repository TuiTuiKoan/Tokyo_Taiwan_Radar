04
03 ・ F — 三種工作型態

F1 穩定可審計 ・ F2 彈性判斷 ・ F3 分辨架構

F1

穩定 ・ 可審計

  • 處理重複/複雜事務
  • 傳統軟體自動化
  • 高度合規要求，要求資料極度精準

→ 常常根本不需要 agent

F2

需要變通

  • 成本較高
  • 需要彈性判斷與複雜考量
  • 沒有標準答案

→ agent 真正的發揮空間

F3

分辨架構

  • 第一件事：分辨它是 F1 還是 F2
  • F1 → 寫死規則 / 傳統程式
  • F2 → 導入 agent
F1、F2、F3 的實際做法差很多 —— 需要理解「功能」要怎麼轉譯，然後思考怎麼做「架構」。

Agent 嵌入在 Workflow 之中
  • Workflow 提供脈絡：Cron 觸發，把原始資料餵給 agent。
  • Agent 執行判斷：annotator 對每筆事件做價值判斷與多語轉換。

11
05 ・ B-1

回頭重看設計的變因

R 需求・F 功能・Be 預期行為・Bs 結構行為・S 結構・D 設計描述。
單箭頭＝轉換，雙箭頭＝比較。

  • 站怎麼運作 ─ F
  • 怎麼打造這個站 ─ S
  • 設計和打造的關係 ─ B
一切都是機率控制。
目標是「縮小負面機率」，最終才逐步「寫死」成規範。
FBS 原則

用 LLM 從「需求 R」直接生成「結構 S」品質往往很差 —— 違背了 FBS「功能無法直接連結結構」的原則，必須經由 Behaviour 中介。

AI 時代的產品開發 = 同時設計四個東西

1

Structure ・ 建造車

IA、page shift、layout、table、conversation design、data model。

2

Dynamic Content ・ 建造導航

generative output、generative UI —— 每次運行都不同的內容。

3

Dev Side ・ 建造工廠

git、skill、history、harness：plan→engineer→tester；plan→critic→engineer→tester→skill feedback。

4

Op Side ・ 建造駕訓班

feedback loop、golden dataset、baseline、metrics、eval（實驗組/對照組，重點在「準」，與 A/B testing 不同）。

BEHAVIOUR13
05 ・ B-3

對應這四個領域 ・ 設計可以做什麼

1

Structure ・ UX 的基礎，但更關心 data

沿用 UX 原本的基礎能力，但更需要關心資料 —— data model、資料品質、結構如何承載內容。

2

Dynamic Content ・ Human-Data Interaction

新：開始關心 human-data interaction —— 人與機率性、生成式內容之間的互動設計。

3

Dev Side ・ 增加 coding 的「經驗」

新：設計師開始累積 coding 的經驗；因為未來所有用戶都可能是開發者，設計必須真正了解用戶。

4

Op Side ・ 結合 Data Science 工作流

新：開始了解 Data Science 的工作流，並結合 UX 實驗一起做驗證（baseline、metrics、eval）。

14
06 ・ 從 0 開始

Planning MVP ・ 先有一條端到端

MVP

從 0 規劃

  • component-architecture（像 full-stack sitemap）
  • 只接 2 個來源起步
  • 先把「端到端」跑通，再談擴張
DevOps

Agent + Workflow

  • 每日排程爬蟲（workflow）
  • 標註 / 翻譯 / 稽核（agent）
  • 失敗自動通知，可審計
原則：先有一個端到端，再逐條 pipeline 演化。
CASE STUDY15
06 ・ Evolving Pipelines

三條演化中的管線 + 可解釋性

Source Research

持續發掘新的台灣相關活動來源並評估。

Annotation

分類、地點、日期、主辦方 —— AI 標註 + 規則校正。

Translation

繁中・日・英三語，鎖定人工修正避免被覆寫。

Explainability + Feedback Loop：每個欄位都能回答「為什麼是這個值」，錯誤能回流成下一輪的規範。
CASE STUDY16
06 ・ 最小範圍測試

電影案例 ・ 畫面元素的來源

用「電影」這個最小範圍當試驗田 —— 範圍小，才看得清楚每個欄位的來源與風險。

日期

開演日 vs 文章發布日？時區偏移？跨日場次？

地點

場館名稱, 地址, 多場地, 線上線下都有?

重複

同來源的多場次、不同來源的同一活動如何去重。

畫面上每個元素，都要問：它從哪來、可不可信、會不會跟別的衝突。
CASE STUDY17
06 ・ 規範設計的核心動作

錯誤的自我學習 ・ 縮小負面機率

Skill ・ History

錯誤自我學習

每次踩到的雷，寫進 history.md；可一般化的，升級成 SKILL.md 規則。

獨立驗證

每日覆盤的 skill

獨立的稽核 agent 每天覆盤，加速發現「靜默失敗」。

縮小負面機率：把 long-tail edge case 寫成 skill 釘住 （例：地址欄位的「線上活動」從沒被規劃進篩選選項）。
但這與真正「寫死」仍有差距 —— 依舊可能犯錯、缺漏，所以才需要持續的獨立驗證。
CASE STUDY18
06 ・ 獨立性 與 共通性

資料來源的獨立性 vs 跨來源的共通性

獨立性

一個來源 ： 一組 skill-history

  • 每個資料來源對應獨立的 agent / skill
  • 針對來源特有的問題與性質進行補強
共通性

跨 agent 的共通 skill

  • 分類設計、地址正規化等共通邏輯
  • 一處修正，全來源受惠
  • 近一步催生分類，架構的更新
CASE STUDY19
06 ・ 架構遷移 與 規模化教訓

架構遷移，模塊演化

  • 共通架構修改：排程型、分類體系的調整
  • 開發 agent 的修改：樹狀平行多工，串流自動規劃→開發→驗證→部署
  • 站台規模錯誤的自我學習（樹狀擴散）
  • 建立 ground truth 表：電影院 / 地址 / 官網 / 片名 / 導演 / 演員，不必每次「重新查」
  • 慘痛教訓：開發兩個月才發現，全站 19 個 button 不是共用統一元件
規範設計的真諦：把一次次的「意外」，沉澱成下一次的「預設」。
